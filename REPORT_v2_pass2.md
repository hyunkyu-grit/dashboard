## Pass A — scale

Synthetic rows are generated by inflating the live `WallSummary` and handing it to
the **real** `buildRows()`; they go through the real comparator, ladder and tint
ramp. Harness at `/scale` (`?n=`, `?d=dense`), not linked from anywhere.

The expanded universe is not built: leg matching, continuous series across
on-the-run changes and quarterly futures rolls are backend decisions outside this
session. Only the shape at that row count is measured.

### A1 — DOM node count of the table subtree

| rows | nodes | per row |
|---|---|---|
| 200 | 8,680 | 43.4 |
| 500 | 21,580 | 43.2 |
| 1,000 | **43,080** | 43.1 |
| 2,000 | 86,080 | 43.0 |

Linear. Identical at both densities — **density changes document height, not node
count.**

### A2 — sort click → DOM reflects the new order

| rows | click returns | DOM updated | threshold |
|---|---|---|---|
| 200 | 4.1 ms | **513 ms** | ≤ 150 ms |
| 500 | 3.6 ms | **1,298 ms** | ≤ 150 ms |
| 1,000 | 4.9 ms | **2,498 ms** | ≤ 150 ms |

**The update is not synchronous.** `click()` returns in ~4 ms with the DOM
unchanged; the new order appears later. As instructed, what was measured is what
actually happens: click → first DOM mutation, via `MutationObserver` (no rAF, no
paint timing). **A2 misses at every size measured, including 200.** It is not a
1,000-row cliff — it is ~2.5 ms per row from the start.

### A3 — rows whose `transform` one FLIP touches

| rows | touched | threshold |
|---|---|---|
| 200 | 200 | ≤ 200 |
| 500 | 499 | ≤ 200 |
| 1,000 | **1,000** | ≤ 200 |

The culling works exactly as written — it skips rows whose y did not change. A sort
by |change| moves essentially every row, so **there is nothing to cull.** The
threshold is unreachable by better culling; it is reachable only by having fewer
rows in the DOM.

### A4 — route bytes, 44-row build vs 1,000-row build

```
44-row build    /scale   1.2 kB   194 kB First Load
1,000-row build /scale   1.2 kB   194 kB First Load    ← identical
```

Rows arrive at runtime, so the row count never enters the bundle. **The entire cost
of scale is DOM and runtime, none of it is shipped JS.**

### A5 — scroll

43,080 after; 1,000 rows before, 1,000 after.** **Nothing is recycled.** This is the
measured form of "CDS `Table` ships no virtualization".

## Pass B — chart

Both candidates drew the same series from `:8200`. Weekly bars are real OHLC from
the backend (553 available). **Daily OHLC is not served** — the backend gives daily
closes and only `w`/`m` candles — so the 2,500 daily bars are derived from the daily
closes (`o` = previous close, `h`/`l` = max/min of `o`,`c`). Node count depends on
bar count, not on values, so this is honest as a rendering benchmark and is not a
price series.

### Candidate A — CDS `CartesianChart` + custom candle layer

| # | Result |
|---|---|
| B1 calendar spacing | **FAIL** |
| B2 nodes at 520 weekly | **1,562 — PASS** (cap 2,000) |
| B2b at 2,500 daily | **not measured** — the chart does not render in the configuration B1 requires |
| B3 zoom + pan | **not measured** — nothing renders to zoom |
| B4 visible-range extremes | **not measured** — same |

The epoch-milliseconds-on-a-linear-scale attempt was made first, as instructed, and
it is the finding:

- With the **default axis**, `getXScale()` maps the data **index**. Feeding it
  `Date.parse(t)` produced bar gaps of ~2.7 × 10⁹ px — the bars are off-canvas and
  the spacing is index-based, which is exactly what B1 rejects. The candle layer
  itself rendered fine here: **1,562 nodes at 520 bars**, two elements per bar.
- With an **explicit** `xAxis={{ id, scaleType: 'linear', domainLimit: 'strict',
  domain: {min: epoch, max: epoch} }}`, the chart renders **an empty `<svg>` with one
  node**. Adding `xAxisId` to the series to bind it to that axis changed nothing.
  No console error. Same at 520 weekly and 2,500 daily.

**Reported as a discrepancy rather than worked around.** No replacement API was
synthesised. The axis-configuration contract that makes a value-domain x scale work
is not derivable from the installed typings, and three attempts did not find it.

For the record, the chart subpath exports are `area`, `axis`, `bar`, `gradient`,
`legend`, `line`, `Path`, `PeriodSelector`, `point`, `scrubber`, `text`, `utils`.
There is no zoom or pan API among them; `PeriodSelector` chooses a period, which is
not wheel zoom and not drag pan.

## Verdicts

### Pass A — the branch was taken

**CDS `Table` holds the markup contract but not the scale.**

A2 misses by 17× at 1,000 rows (2,498 ms vs 150 ms) and misses at 200 rows too.
A3 touches 1,000 rows where 200 is the cap, and culling cannot close it because a
re-sort moves every row. A5 shows nothing is recycled: 43,080 nodes stay in the DOM.

The recommended shape is **a headless table (TanStack) supplying rows and
virtualization inside CDS chrome.** **Not implemented here** — it is a different
architecture and earns its own pass.

**The V2 guards survive that branch.** Sort key, column ladder, colgroup single
source and sticky opacity were all written against the *contract* — the comparator,
the ladder function, the `<colgroup>`, the surface token — not against CDS
components. A headless table swap changes who renders the rows, not what the
contract says.

### Pass B — the candidate is B

Candidate A fails B1 and B3/B4 were not measurable, so the rule ("A passes only if
B1, B3 and B4 are all true and B2 is under cap") is not met. **The CDS chart is out
of scope for this product**, on the evidence that it renders an empty `<svg>` in the
only axis configuration that could give calendar spacing, and index spacing in the
one that renders.

Both candidates are committed. The loser is not deleted — `/chart?c=a` still runs.
